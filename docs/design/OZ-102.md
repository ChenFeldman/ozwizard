# Design note — OZ-102: making large scans fast

**Status:** accepted · **Ticket:** [OZ-102](../../tickets/OZ-102.md)

## The problem, measured

A scan of a large artifact is slow in proportion to the number of resolved
dependencies. The time is **not** in the matching. Matching a dependency against the
advisory list is a handful of string comparisons per record — microseconds, and it
scales fine.

The time is in the **advisory lookup**: one upstream feed round-trip per dependency.
N dependencies today cost N sequential round-trips. That is the entire cost, and it is
the only thing worth fixing.

## Where the fix belongs

**At the fetch and repository boundary — not in `src/core/`.**

The slow part is IO, and IO does not live in core. Concretely:

- The unit of work to overlap is "fetch the advisory records for package X". That is a
  network call. It belongs behind the advisory-fetch boundary, alongside the other IO
  the service does, where it can also be given a timeout, a retry, and a cache.
- Core's job is to take advisory data that has **already been gathered** and turn it
  into findings and a verdict. It should receive the data, not go and get it.

So the shape of the fix is: gather the advisory data for the whole resolved set at the
IO edge (bounded, so a 400-dependency artifact does not open 400 sockets), hand the
gathered result to core, and let core stay a pure function over it.

## Why core must stay pure and deterministic

This is not style. Policy verdicts are the product — `allow`/`warn`/`block` decides
whether an artifact ships, and an escalation is a human overriding one on the record.
That only works if a verdict is **reproducible**: the same manifest and the same
advisory data must produce the same findings, in the same order, on any machine, today
and when someone re-derives the decision in six months.

Introducing scheduling into `src/core/` breaks that in two ways:

1. **Ordering becomes timing-dependent.** Findings accumulate in whatever order the
   in-flight work settles. Two runs over identical input produce the same set in a
   different order — which is a different stored `scan` record and a different diff in
   review, for no behavioural reason.
2. **Core stops being testable without IO.** The current core functions are tested by
   passing data in. Put the fetching inside them and every test needs a fake clock or
   a fake feed, and the "same input → same output" guarantee is gone.

`.claude/rules/core.md` carries this as a hard rule for `src/core/**`: no IO, no
ambient state, deterministic output. OZ-102 is a performance ticket; it does not buy
an exemption from it.

## Explicitly rejected

- **Overlapping the loop inside `scanDependenciesLive`.** This is the obvious-looking
  spot — the serial `await` is sitting right there. It is the wrong spot: it puts
  scheduling and IO into the pure layer, and it makes the result order depend on
  network timing. Rejected.
- **Putting a bounded worker pool in `src/core/`.** Bounded mapping over an array is a
  generic utility, not scan logic. Wherever one comes from, its home is `src/util/`
  alongside the other shared helpers — never inside the domain layer.

## Acceptance

- Wall-clock for a large artifact drops from N round-trips to roughly N/limit.
- Findings and verdicts are byte-identical to today's, including order.
- `src/core/` gains no IO, no timers, and no scheduling.
